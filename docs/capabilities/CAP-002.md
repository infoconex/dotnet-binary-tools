# CAP-002: Assembly Inspection

**Specification status:** Approved for v0.1. **Implementation and acceptance:** Planned, not yet verified.

[Capability index](README.md)

This document explains the approved capability boundary. The [functional requirement catalog](../requirements/functional.md) and linked Given/When/Then scenarios provide the authoritative acceptance contract; explanations here must not expand it.

## Purpose

Determine what trustworthy metadata a selected compiled file actually contains, including its declared .NET target framework, without loading or executing the file. This capability is the source of assembly facts; it does **not** decide what runtime is installed, requested by deployment configuration, or actually running.

## Approved behavior

- **Static evidence only:** Read PE/CLI metadata from the file as data. Never load inspected assemblies, invoke entry points, execute code, or resolve references by loading candidate binaries.
- **Explicit classification:** Distinguish a managed assembly, a native/non-managed candidate, corrupt or unrecognized content, and an unreadable file. A valid native DLL/EXE is not a malformed .NET assembly merely because it has no CLR metadata.
- **Target declaration:** Preserve the exact `TargetFrameworkAttribute` moniker and its evidence source. Recognize .NET Framework, .NET Core, modern .NET (5+), and .NET Standard families where declared, while retaining future or unfamiliar monikers without inventing interpretations.
- **Unknown remains unknown:** Missing `TargetFrameworkAttribute` means unknown declared target. Do not infer a target from CLR metadata version, assembly references, API usage, filename, neighboring files, or other heuristics.
- **Assembly identity:** Return available simple name, assembly version, culture, public-key token, and complete identity. Optional informational/file version, company, product, and description fields are returned only when actually present.
- **Execution-related metadata:** Report PE machine architecture, managed execution flags, and whether an entry point is declared. These are metadata facts, not proof of eventual process bitness or execution environment.
- **Reference inventory:** Report direct declared assembly references. Do not construct a full dependency graph or infer that an adjacent native apphost belongs to a particular managed DLL.
- **File facts and hashing:** Include permitted basic file facts. Calculate SHA-256 only on explicit request and within established resource/read-failure safeguards.
- **Partial metadata:** Preserve fields reliably read when other optional fields are malformed, with field-specific diagnostics. Do not manufacture reliable findings from unreadable data.

## Inputs and outputs

Receives a validated individual file from [CAP-001](CAP-001.md), either directly through `inspect` or as a candidate from [CAP-005](CAP-005.md). Produces classified, evidence-backed metadata findings for downstream inventory and reporting.

## Boundaries and exclusions

This is metadata-only inspection, **not** disassembly, source-code analysis, process execution, dependency resolution, installed-runtime detection, or inferred application grouping. [CAP-003](CAP-003.md) reads deployment configuration separately; [CAP-004](CAP-004.md) assesses lifecycle separately.

## Failure and completeness behavior

Keep non-managed, corrupt, and unreadable outcomes distinct. Record field-level errors and trustworthy partial data; a single candidate's failure need not invalidate an otherwise valid multi-file scan.

## Related capabilities

[CAP-003 deployment configuration](CAP-003.md), [CAP-004 lifecycle assessment](CAP-004.md), [CAP-005 inventory](CAP-005.md), and [CAP-006 reporting](CAP-006.md) consume these facts without silently changing what the metadata proves.
