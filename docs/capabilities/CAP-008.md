# CAP-008: Distribution

**Specification status:** Approved for v0.1. **Implementation and acceptance:** Planned, not yet verified.

[Capability index](README.md)

This document explains the approved capability boundary. The [functional requirement catalog](../requirements/functional.md) and linked Given/When/Then scenarios provide the authoritative acceptance contract; explanations here must not expand it.

## Purpose

Deliver the same CLI product through independently runnable, platform-specific Native AOT executables and a NuGet .NET Tool, with release claims backed by real consumer evidence rather than project settings alone.

## Approved distribution identity

| Item | Approved v0.1 identity |
| --- | --- |
| Executable and tool command | `dotnet-binary` / `dotnet binary` |
| NuGet package ID | `Infoconex.DotNetBinary.Tools` |
| Standalone targets | `win-x64`, `linux-x64`, `osx-x64` |
| Deferred platforms | ARM64 and any platform/RID without independent acceptance evidence |

## Approved behavior

- **Standalone executable:** Publish appropriately packaged Windows, Linux, and macOS x64 Native AOT outputs, each verified to launch independently on its corresponding platform.
- **Installable .NET Tool:** Build a RID-aware NuGet tool under the approved ID. Verify package selection, installation, command dispatch, and execution on each supported OS. Installation of a .NET Tool may have different host/SDK prerequisites from running a standalone executable.
- **Behavioral parity:** For the same version and fixtures, standalone binaries and the NuGet tool must expose identical functional commands and report contracts. Packaging is not permission to diverge.
- **Trustworthy artifacts:** Produce versioned platform-specific assets, verifiable package contents, checksums, and appropriate provenance without advertising unverified architectures.
- **Clean consumer verification:** Demonstrate that each standalone AOT binary runs without a separately installed .NET runtime on a suitable clean consumer. Separately verify NuGet tool installation and invocation requirements.
- **Real platform gates:** Require native publish, executable smoke tests, and relevant feature acceptance on each advertised RID; an ordinary managed build cannot substitute for native verification.
- **Controlled release:** Tagging, public release, package publishing, and ARM64 expansion require separate owner authorization and evidence. Do not publish from draft PR CI.

## Inputs and outputs

Consumes the approved CLI and its release-ready tests, producing versioned, platform-appropriate distributables and verification records. Consult [packaging guidance](../engineering/packaging.md) and [release gates](../engineering/release-gates.md) for operational expectations.

## Boundaries and exclusions

A successful AOT compiler invocation or a help/version smoke test **does not prove** functional acceptance, clean-runtime independence, installed-tool dispatch, or package publication. Do not claim that a package is reserved, published, or compatible with a platform solely from metadata declarations.

## Failure and completeness behavior

A failed RID-specific build, runtime-free consumer test, tool install/invocation, package-integrity check, or functional-parity gate blocks claiming release acceptance for that platform. Record the actual artifact version, target RID, execution environment, and exact commit evidence used for each claim.
