# CAP-006: Results and Reporting

**Specification status:** Approved for v0.1. **Implementation and acceptance:** Planned, not yet verified.

[Capability index](README.md)

This document explains the approved capability boundary. The [functional requirement catalog](../requirements/functional.md) and linked Given/When/Then scenarios provide the authoritative acceptance contract; explanations here must not expand it.

## Purpose

Present the same underlying inspection facts consistently to humans, scripts, and automation. Reports must preserve evidentiary distinctions, errors, and coverage limitations rather than promoting uncertain or partial results into confident conclusions.

## Approved behavior

- **Common contract:** `inspect` and `scan` use a single documented, versioned JSON report envelope containing command, selected inputs, generation metadata, completion, summary totals, per-file findings, and applicable lifecycle-dataset provenance.
- **Human-readable output:** Produce a concise readable summary by default. `--details` expands available metadata but does not change inspection decisions or the underlying facts.
- **Machine-readable output:** `--format json` writes exactly one syntactically valid JSON document, with no incidental log text or diagnostic prose in the JSON stream.
- **Selective fields:** `--fields` projects supported per-assembly fields in both human and JSON views. It must not remove report-envelope facts such as command identity, input coverage, totals, completion state, or dataset provenance.
- **Option compatibility:** Reject unsupported projected field names and incompatible `--details` / `--fields` combinations through the CLI validation contract.
- **Explicit exceptional outcomes:** Keep unknown targets, non-managed candidates, malformed metadata/configuration, skipped paths, failures, and partial-coverage warnings visible in the report along with applicable evidence and diagnostics.
- **Output destinations:** Write to stdout by default. `--output` directs a human or JSON report to the selected file; diagnostic messages are reserved for stderr.
- **Never overwrite an existing report:** If the requested output path already exists, create a distinct filename using a UTC timestamp and collision-resistant suffix with exclusive creation. Do not overwrite another process's report due to a time-of-check/time-of-use race.
- **Large inventories:** Render without requiring the complete serialized inventory to be held in memory at once. A write/serialization failure is an explicit reporting failure, not a success.

## Inputs and outputs

Consumes structured findings, summaries, completion metadata, and provenance produced by [CAP-005](CAP-005.md), [CAP-002](CAP-002.md), [CAP-003](CAP-003.md), and [CAP-004](CAP-004.md). Produces either a readable report or the versioned JSON document to stdout or an explicitly selected report file.

## Boundaries and exclusions

Reporting must not re-parse inspected binaries, fabricate missing metadata, classify lifecycle without source evidence, reinterpret failures as success, or infer that a requested runtime is installed. Field projection affects presentation only.

## Failure and completeness behavior

Per-candidate inspection failures can coexist with a valid report and an exit code of zero. Invalid rendering options, unwritable output locations, serialization failures, and unrecoverable report errors cause command failure. Report completeness remains explicit even when the process exits successfully.
