# CAP-007: Command-Line Interface

**Specification status:** Approved for v0.1. **Implementation and acceptance:** Planned, not yet verified.

[Capability index](README.md)

This document explains the approved capability boundary. The [functional requirement catalog](../requirements/functional.md) and linked Given/When/Then scenarios provide the authoritative acceptance contract; explanations here must not expand it.

## Purpose

Provide a discoverable, predictable command surface for the planned inspection functions. The CLI translates arguments into application requests, presents help and diagnostics, and maps outcomes to process exit codes; it must remain a thin adapter, not a second implementation of inspection logic.

## Approved command surface

The .NET Tool command is `dotnet binary` and the underlying executable name is `dotnet-binary`. The planned operations are:

```shell
dotnet binary inspect ./bin/MyLibrary.dll
dotnet binary scan ./applications --recursive
dotnet binary --help
dotnet binary --version
```

The `inspect` and `scan` examples express **approved future behavior, not implemented commands**. At the current engineering foundation, the CLI supports help/version only, and unsupported operations fail explicitly.

## Approved behavior

- **Input arity:** Parse exactly one explicit file argument for `inspect` and one or more explicit directory arguments for `scan`. Delegate filesystem validation to [CAP-001](CAP-001.md).
- **Relevant options:** Expose approved controls for recursion, linked-directory traversal, explicit configuration for `inspect`, output format, concise/detailed metadata, projected fields, output filename, limits, opt-in hashing, and explicitly requested lifecycle-data refresh.
- **Early errors:** Reject unknown flags, missing option values, incompatible switches, and incorrect input counts before starting expensive work, with actionable diagnostics.
- **Help and version:** Document syntax, safety restrictions, defaults, report formats, and the opt-in network refresh behavior; display version information accurately.
- **Output discipline:** Keep reports on stdout or at the requested output path and diagnostics on stderr. Avoid ANSI decorations or progress noise corrupting machine-readable streams.
- **Exit semantics:** Return zero for a successfully generated report, including one with per-candidate errors or incomplete scan coverage. Return nonzero for invalid inputs, malformed options, and unrecoverable command/reporting errors.
- **Architectural ownership:** Delegate use-case orchestration to Application ports and services. The CLI must not own PE parsing, runtime-configuration interpretation, lifecycle rules, directory-inventory logic, or report persistence.

## Inputs and outputs

The CLI receives user arguments and selects an application use case. It emits help/version text, a structured result rendered by [CAP-006](CAP-006.md), or a diagnostic/exit status according to the command contract.

## Boundaries and exclusions

No automatic execution of inspected binaries and no silent network access. A help message advertising planned behavior must identify it as unimplemented until tests demonstrate the feature. An inspect invocation is not source-code analysis.

## Failure and completeness behavior

Wrong command syntax and invalid explicit roots are command failures; partial discovery findings in an otherwise valid report are not. Preserve distinction between stderr diagnostics and the factual status recorded in a JSON report.

## Open implementation decisions

Exact aliases for arguments and final JSON contract spelling are [not yet finalized](../requirements/open-decisions.md). Approved command names and the `dotnet-binary` executable identity are already fixed by the specification.
